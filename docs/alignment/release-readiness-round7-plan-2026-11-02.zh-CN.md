## 2. 下一轮验收档：先锁定口径，再正式采集

按上轮讨论，提出 **R2-60 基础发布档**：面向 60fps 使用体验，保留 120Hz 增强目标及原 D1 优化目标。**本计划中的 R2 是拟采用的独立发布标准；原 PRD/D1 冻结表、旧制品与历史失败记录保留。** R7-01 完成时将最终采用的支持范围、阈值和测量方法记录成版本化验收清单，之后不因采样结果改变门槛。

### R2-60 拟定门槛

| 项目 | 发布要求 | 完整性条件 |
|---|---|---|
| CPU 帧 P95 | 普通与压力负载均 ≤16ms | 使用官方 FrameTiming；CPU ≤10ms 继续作为优化目标，CPU 达标同时还须满足实际呈现门槛。 |
| 普通负载正 overrun | ≤5% | 对系统分配的实际帧 deadline 计算；至少两次独立采集，每次均通过。 |
| 极限压力正 overrun | ≤10% | 同上；保留所有匹配帧、完整 trace 与分母。 |
| 静态轻载输入到呈现 P95 | ≤80ms | 每次 100/100 精确关联；最终执行两次独立采集。 |
| 压力输入到呈现 P95 | ≤100ms | 每次 100/100 精确关联；最终执行两次独立采集。 |
| 冷启动完整图表 TTFD P95 | ≤1500ms | 每台机 5 个有效冷启动样本；TTID 独立记录。 |
| 严格 warm TTFD P95 | ≤500ms | 每台机 5 个有效样本；每个预热/测量对保持同 PID，测量包含 Activity 重建与完整图表绘制。 |
| 100k 加载就绪 P95 | ≤2500ms | 每台机 5 个独立进程样本；首批可交互及全量就绪分开记录，全量就绪不是 TTFD。 |
| B-04 突发收敛 | ≤2s | 最后一个已接受操作至最终一致快照；不丢已接受数据或重排回调。 |
| B-05 释放 | 0 确定泄漏，retained ≤5MiB | 每台机最终 R8 包 30 次建销、同一 facade 100 次真实 setSymbol，实际 heap 与弱引用共同验证。 |
| B-06 热稳定 | 30 分钟无崩溃、ANR、无界增长 | 每台机留存进程、内存分类与温度时间序列；有增长须解释归因和边界。 |
| 正确性、布局与可访问性 | 无阻塞缺陷，关键用例全部通过 | 大字体横屏、图例首帧/缓存、可见命中区域、PNG、画线、数据切换和 TalkBack。 |

启动、容量与输入的宿主 P95 使用 inclusive 插值并保留全部原值；官方帧 P95 保留 AndroidX 输出。五样本 P95 是小样本结果，遇到失败或明显波动先定位原因，再完整重跑一组，既有失败仍归档。跨设备、跨模式、跨构建不合并计算分位数。

### 60fps 档的必要条件

1. 库与示例/宿主的职责必须明确：库不擅自修改全局系统刷新率。若采用 60fps 策略，应在实际示例/宿主运行路径中实现并验证，按支持的 Android API 保持兼容。
2. 系统实际授予的刷新率、应用目标节奏及 FrameTimeline deadline 必须留证。只在 benchmark 中手动锁 60Hz 得到的数据属于模式实验，不能直接证明默认产品已达标。
3. 若默认仍运行于 120Hz 且没有可交付的 60fps 策略，按该真实模式的 deadline 验收；不得把 120Hz 的超时帧事后套用 16.7ms 改判通过。
4. 120Hz 增强测试单列结果与支持声明。只有基础发布路径真实满足门槛、且未宣称全面高刷达标时，120Hz 增强目标才可作为后续优化项。

刷新率与帧预算依据：[Android 慢速渲染说明](https://developer.android.com/topic/performance/issues/render)、[高刷新率渲染说明](https://android-developers.googleblog.com/2020/04/high-refresh-rate-rendering-on-android.html)。上述项目阈值属于本项目的产品取舍，不是 Android 官方推荐门槛。

## 3. 固定负载与对照纪律

| 负载 | 定义 | 用途 |
|---|---|---|
| S0 默认使用 | 初始500 candle、默认 MA/VOL/MACD、200ms/tick；记录期间实际数据量与更新次数 | 真实使用路径的帧与稳定性检查，确认静态夹具未掩盖实时问题。 |
| S1 静态轻载 | 1000 candle、1 个 MA、0 overlay、VOL/MACD 与三 pane | 正式普通帧、轻载输入，沿用已有独立输入驱动。 |
| S2 静态压力 | 50k candle、10 个 MA 实例总数（含默认 MA）、另有 VOL/MACD、100 segment、三 pane | 正式压力帧与压力输入；20 次滑动，保持既有步数、等待与种子。 |
| S3 容量 | 100k candle、10 个 MA、VOL/MACD、100 segment | 冷加载分项、首批交互与全量就绪。 |

- 每次优化前后的对照使用同一设备、同一测量模式、同一版本测量工具和同一负载；先验证测量可用，再比较实现。
- 工具链或计量配置发生变化时，先用未改生产源码的 rc4 建立新旧工具对照，再做修复前后对照，避免混淆工具收益与产品收益。
- 正式目标是手动安装的非 debuggable、R8 + 资源压缩 release；记录目标 APK、benchmark APK、mapping、来源快照与 Maven 制品 SHA。禁止由 connectedBenchmark 自动换成未压缩目标。
- 同一手机采性能时不并发安装、heap dump、UI 检查或其他测量；温度、充电、CPU 锁定状态、后台策略和实际刷新率随每组留档。
- 每组完成立即拉取 JSON、trace 和样本文件，核对数量、哈希与可解析性后才启动下一组，避免再次被采集工具清理原始 trace。

### 暖启动问题的处理边界

先证明当前采集为何无法产生指标；优先修复测试工具、捕获配置或调用时序，避免为满足 benchmark 改写生产启动流程。AndroidX/TraceProcessor 变更若确有必要，应单独留档版本、原始查询和 rc4 对照，不顺带升级生产依赖。离线 startup 表、五份 trace、JUnit 完成或应用“看起来启动正常”都不等于取得五个正式 TTFD。

### 优化代码的验收边界

保持原有分层与主要调用顺序。涉及缓存、裁剪或批处理时，需覆盖失效条件、首帧/缓存重放、字体/旋转、数据切换和导出；涉及后台计算时，需覆盖最终一致快照、取消、旧会话隔离与回调顺序。只有与实际改动相关的新增回归才进入本轮测试，测试数随执行结果统计。历史独立回归没有可复现源码/脚本时，列为需恢复资产，不能直接计入本轮通过数。
